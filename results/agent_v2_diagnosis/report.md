# Agent V2 失败复盘：为什么阶段切换任务输了

**主要问题是探索决策：Agent 把一些局部失败推广得过宽，放弃了有潜力的中间方案；最终停在一个单步修改无法改善的位置。反馈也存在不足：总分看不出前一批请求积压对后一批的影响。** 补测支持这两项诊断，但还不能证明增加反馈或修改提示就能让下一轮 Agent 获胜。

这是对已知 T04 开发样例的事后分析。原比赛仍是 Agent **574**、无反馈候选 **550**、最佳局部搜索 **540** 周期，越小越好。没有把事后找到的方案改写成 Agent 当时的成绩。

## 1. 哪次判断漏掉了机会

地址位排列在下表写成 `[两位 channel | 一位 bank | 一位 column | 两位 row]`。数字是原始块地址的位编号；改 column 位必然同时改变 row 位分配，并非单独改变一个硬件参数。

| 原搜索记录 | 当时结果 | 事后受控修改 | 补测结果 |
| --- | ---: | --- | ---: |
| 第 3 次：`[2,4 | 3 | 1 | 0,5]` | 646 | 交换 column 的位 1 与 row 的位 0 | **550** |
| 第 6 次：`[5,4 | 2 | 3 | 1,0]` | 618 | 交换 column 的位 3 与 row 的位 0 | **540** |
| 第 10 次：`[5,2 | 4 | 3 | 1,0]` | 618 | 交换 column 的位 3 与 row 的位 0 | **540** |

这三个中间方案都不如 Agent 当时已经找到的最好方案，因此未被继续沿这条方向探索。但每个方案都只差一步就能超过最终成绩。

原记录中，第 6 次之后 Agent 回到较好的起点，更换 column 得到 705；第 18、19 次在其他组合下使用 column 位 0，又得到 766、670。失败本身是真的，**“这次组合失败”却不能推出“这个位在其他组合里也没有价值”**。Agent 总共尝试过三次 column 位 0，所以问题不是根本没有想到它，而是没有覆盖它与其他字段的有效组合。

做一个固定 bank 位 3 的四格对照，只改变 channel 组合及 column/row 分配：

| channel 使用的位 | column 位 1 | column 位 0 | 改为位 0 的收益 |
| --- | ---: | ---: | ---: |
| 4、5 | 705 | 705 | 0 |
| 2、4 | 646 | **550** | 减少 96 周期 |

**同一改动是否有效，取决于其他字段。** 这比简单判断“高活动位好”“低活动位坏”更符合这条轨迹的实际行为。

## 2. 为什么只围绕当前最好方案继续试，也不够

利用原实验搜索结束后保存的 720 个排列结果，检查了每个 Agent 候选的全部 15 个单次交换邻居，没有重新运行精确枚举。

- 第 9 次找到的 **585**：没有任何单次交换能严格改善。
- 第 15 次找到的最终 **574**：也没有任何单次交换能严格改善。
- 第 6、10 次的 **618**：各自存在直接到达 **540** 的单次交换。

从最终方案出发，有一条两步路径：

`574：[4,5 | 1 | 2 | 0,3]` → `618：[4,5 | 2 | 1 | 0,3]` → `540：[4,5 | 2 | 0 | 1,3]`

第一步变差，第二步才变好。Agent 可以一次提出联合修改，也可以保留中间方案；不要求必须真的花两次评价沿此路径执行。这里的重点是：**当前最好分数不足以代表一个方向是否值得继续探索。**

普通局部搜索也可能遇到这个问题。本轮对照包含启发式起点和周期性随机重启，并非始终只做贪心改进。三个局部搜索都先评价了 586 的联合统计启发式；种子 0、1 分别从该方案交换不同的一对位找到 540，种子 2 找到 550。Agent 可以使用同一启发式工具，但没有评价这个具体起点。这个差异属于工具选择与预算分配，不是 Agent 没有获得原始轨迹。

上述“局部最优”仅针对单次交换邻域。这是离散排列搜索，不能直接套用连续凸优化的定义；可以确定的是，本例并非从任意当前最好方案都能靠单步改善走到全局最好。

## 3. 总分掩盖了什么

T04 前 96 个请求在周期 0–11 到达，后 96 个在周期 12–23 到达。**第二批开始到达时，前一批 96 个请求全部尚未完成。** 因此，这个任务表示“请求提交模式切换、队列继续积压”，不是两段互不干扰、分别执行完毕的工作负载。

新工具从一次完整模拟的事件记录中，按请求所属批次统计命中、排队和完成时间；不在中间清空队列或重置行状态。

| 方案 | 全部完成时间 | 第一批最后完成时刻 | 第一批行命中率 | 第二批平均请求延迟 |
| --- | ---: | ---: | ---: | ---: |
| Agent 最好 | 574 | 282 | 75% | 419.12 |
| 无反馈最好 | 550 | 258 | 75% | 394.75 |
| 局部搜索最好 | **540** | **215** | 75% | **362.92** |

这些方案第一批行命中率相同，处理速度却明显不同；bank 的分工与时序仍然重要。第二批的延迟包含前一批留下的排队，不能只归因于第二批访问本身。

再把每一批分别从空队列、未打开行的状态运行，作为诊断对照：

| 方案 | 第一批单独运行 | 第二批单独运行 |
| --- | ---: | ---: |
| Agent 最好 | 282 | **284** |
| 无反馈最好 | 258 | 285 |
| 局部搜索最好 | **215** | 324 |

局部搜索的最好方案，**单独处理第二批反而更慢**，但在完整任务上更快。证据支持这样的解释：更快处理前一批、减少积压，是它获益的重要部分。“最终完成更快”不能简单解释为“第二阶段服务更快”。单独运行会改变队列和行状态，两列不能相加充当原任务的耗时分解。

因此分批反馈有诊断价值，但尚未做“给 Agent 看或不给它看”的新任务实验，不能宣称反馈缺失是失败的唯一原因。

## 4. 已落地的改进与下一轮检验

已新增两个可复用产物：

1. [诊断工具](../../hbm_toy/agent_v2_diagnosis.py)：重放候选、按请求批次提取连续执行中的反馈、做冷启动对照，并核验原实验未变化。`phase_feedback` 可供下一版接口复用；**当前冻结的 V2 会话接口没有自动增加这些字段**。
2. [下一版 Agent 提示草案](../../examples/agent_v3_prompt.md)：要求区分事实与假设、限定失败结论适用范围、保留其他探索方向、说明每次实验的用途。没有写入本例的位编号、好方案或固定搜索路线；改进是否有效尚待检验。

下一轮应分开检验两个因素，避免同时改完后无法判断是哪项有效：

| 条件 | 原有汇总反馈 | 增加分批排队与时序反馈 |
| --- | --- | --- |
| 原提示 | 对照 | 单独检验信息增益 |
| 新提示 | 单独检验探索方式 | 检验两者组合 |

四组使用相同任务、设计空间、共同起点和每任务 20 次预算。随机/局部搜索与无反馈提案继续保留，启发式工具对双方开放；工具触发的任何额外后端执行都计数。若从同一次模拟直接提取事件，无需增加模拟次数，但仍记录日志处理开销；单独重跑一批则另计一次。

新任务需要同时包含高积压、较低注入速率，以及阶段间有间隔的情况，避免把 T04 这种强积压情况代表所有“阶段切换”。分批边界/统计窗口在搜索前约定，不能根据答案选择。本轮五条轨迹及它们已知的好方案只作开发数据；多次模型运行应使用独立上下文，当前已看过答案的对话不能充当独立复测。

验收看同预算的最好完成时间、达到目标所需评价次数及独立运行的分布，不把解释变长或诊断指标变多算作成功。若新提示仅在旧 T04 上有效，也不算泛化收益。完成这一轮后，再用真实请求与 Ramulator 检查这些性能关系是否成立。

## 5. 复现与成本

原始输入：[V2 归档](../agent_v2_pilot/report.md)。本次机器可读结果：[diagnosis.json](diagnosis.json)，包含全部 20 次 Agent 决策的原始假设、邻域审计、补测方案及分批指标。

在项目根目录使用一个尚不存在的输出目录：

```powershell
python -m hbm_toy.agent_v2_diagnosis --output results/run_v2_diagnosis_replay
python -m unittest discover -s tests -v
```

本次另外执行 **29 次完整轨迹诊断 + 8 次单批冷启动对照 = 37 次后端调用**。精确邻域查询复用原先已揭示的结果；没有新增 Agent 搜索，没有改写原 20 次预算，也没有再次做 720 项枚举。

工具校验原源码/轨迹/冻结候选哈希，并核对原 `comparison.json` 在诊断前后的 SHA-256。所有补测分数与原排列参照一致，历史候选的完整汇总指标也一致。21 项测试通过，其中新增手算用例检查跨批次保留队列/行状态、延迟分解与事件完整性。

`.gitattributes` 对作为哈希来源的原 `comparison.json` 保留文件字节，避免跨平台拉取时自动转换换行导致哈希不一致。原比赛数据内容没有改动。
