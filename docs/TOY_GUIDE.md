# 玩具版本：运行与实验约定

这是一个固定布局、静态映射、单一介质的流程原型。核心代码只依赖 Python 3.10+ 标准库；已在本机 Python 3.10.11 运行。安装了 matplotlib 时会额外生成曲线图，不安装也能完成实验。

它现在承担基础对照、反馈接口和搜索诊断平台的职责。长期研究转向有系统取舍的内存策略探索，原因和任务选择见[研究定位](RESEARCH_POSITIONING.md#literature-to-principles)。本指南保留现有可运行契约，并在[后续模型契约](#future-model-contract)中说明精读结论对新开发的要求；不会将新设想混入旧 DSL 或旧实验成绩。

## 实验范围

数据布局决定 K/V 如何分块；介质放置与分配决定数据在哪里；地址映射决定物理地址对应哪个 channel/bank/row/column；请求调度决定执行顺序。当前只搜索其中的**静态地址映射**，其他层固定。平台暂时假设允许改变控制器映射，实际硬件仍需核对能力边界。

每个候选从相同初始状态开始独立实验，过程中不切换映射。V2/V3 的阶段变化也属于多阶段流量上的静态策略选择。动态映射需要处理已有数据迁移、旧地址解释和切换成本；多介质还涉及容量、带宽和放置代价。这些不是默认下一项功能，应先证明所选子问题确实需要它们。

## 从这里运行

在项目根目录打开终端：

```powershell
python -m unittest discover -s tests -v
python -m hbm_toy evaluate examples/identity.json --workload stride
python -m hbm_toy evaluate examples/stride_xor.json --workload stride
python -m hbm_toy benchmark --budget 20 --count 768 --seeds 0 1 2
```

最后一条命令自动建立带时间戳的 `results/` 子目录，保存 `report.md`、`benchmark.json` 和逐次候选记录。显式指定 `--output` 时须用新目录，避免覆盖实验。可用 `python -m hbm_toy --help` 查看入口。

已运行的结果见 [首轮实验解读](INITIAL_RESULTS.md)、[完整基线报告](../results/baseline_v2/report.md)。`baseline_v1` 保留补充较强启发式之前的结果。

## 当前对话作为模型提出候选

用户选择先通过文件接口使用当前对话，无需配置模型 API。程序负责确定性执行；模型读反馈、写下一份提案并调用命令。项目没有常驻模型服务，也没有独立的性能/RTL 子 Agent。

```powershell
python -m hbm_toy session-init results/my_session --workload kv_interleaved --budget 20
```

然后按下面的顺序循环：

1. 模型读取 `results/my_session/feedback.json`：包含固定配置、地址位活动、访问样本、历史指标、剩余预算和 DSL 规则。
2. 模型在新的 JSON 文件中保存假设、预测和 DSL。可参考 [提案示例](../examples/proposal.json)，注意示例针对固定步长，不保证适合其他负载。
3. 运行 `session-step`，读取更新后的反馈，再决定下一次修改。

```powershell
python -m hbm_toy session-step results/my_session --proposal examples/proposal.json
python -m hbm_toy session-finish results/my_session
```

`session-finish` 选择训练访问流上完成时间最短的候选，关闭搜索，最后在变体负载上评价一次并输出 `result.json`。关闭后不能继续提交。以上两条命令不是要求只搜索一步；应在多轮 `session-step` 完成后再结束。

提案格式：

```json
{
  "hypothesis": "固定步长使 channel 选择位不变化，可能造成拥塞",
  "expected": "把较高位混入 channel 后，请求分布应更均匀",
  "dsl": {
    "version": 0,
    "operations": [
      {"op": "xor_bit", "dst": 0, "src": 6},
      {"op": "xor_bit", "dst": 1, "src": 7}
    ]
  }
}
```

可给下一次模型对话的简短任务说明：

> 只读取本次 session 的 feedback.json、DSL 规则与训练指标。保持工作负载和配置不变，提出不超过 max_operations 的候选；评价前先保存 hypothesis、expected、dsl。每轮读取反馈再修改。遵守剩余评价预算，不读取测试负载、其他实验的测试结果或修改评价器。结束后才调用 session-finish。

这是实验纪律，不是文件系统权限隔离。严格的盲测还需要把生成器和测试集放到模型不可读的独立评价环境。当前首轮对话参与了实现且看到其他基线报告，因此不构成严格盲测。文件协议不记录对话 token、费用、精确模型版本或完整提示上下文；相关字段为空，不应按零成本解释。

## 固定请求轨迹与 Agent V2

文件接口现在可用 `session-init --trace` 读取外部 JSON 轨迹。示例格式如下；`address` 是字节地址，必须按配置中的 `granule_bytes` 对齐，`arrival` 是非负的玩具时间，`request_id` 唯一。`kind` 和 `stream` 可省略，默认为 `read` 和 `0`。

```json
{
  "version": 1,
  "requests": [
    {"request_id": 0, "address": 0, "arrival": 0, "kind": "read", "stream": 0},
    {"request_id": 1, "address": 64, "arrival": 0, "kind": "write", "stream": 0}
  ]
}
```

将轨迹保存为 `trace.json`，使用默认配置启动：

```powershell
python -m hbm_toy session-init results/my_trace_session --trace trace.json --budget 20
python -m hbm_toy session-step results/my_trace_session --proposal examples/proposal.json
python -m hbm_toy session-finish results/my_trace_session
```

这里的提案示例只说明命令用法，仍需根据实际轨迹生成候选。自定义配置使用全局 `--config` 参数；例如六位小试验的配置为 `{"channel_bits":2,"bank_bits":1,"column_bits":1,"row_bits":2}`，其他字段沿用默认值。

- 初始化会校验请求并复制为会话内的 `trace.json`，后续只评价该固定快照；改动外部原文件不影响会话，改动会话快照会触发哈希错误。
- `feedback.json` 包括整体及四个窗口的活动统计、地址位成对联合分布和全部已执行候选反馈，不包含精确最优或其他方法的结果。原始快照可供各方法使用。
- 默认 `--space linear` 允许交换与 XOR；`--space permutation` 只允许交换。线性模式的共同起点是 identity / row-XOR，排列模式是 identity / reverse-bits，均计入预算。
- V2 每次实际后端调用计入预算，包含失败调用；同一语义映射的缓存命中与非法提案不计数，提案总数最多为预算的 10 倍。失败和缓存状态分别记录。
- 固定轨迹模式的 `session-finish` 仅关闭搜索并保存最佳候选，**不会伪造一个测试集或额外运行合成变体**。若需要泛化评价，应另行冻结有来源的验证轨迹。

四步小试验由 `python -m hbm_toy.agent_v2 prepare/start/compare --output <新目录>` 组织：先生成任务与统计，再由外部模型冻结全部无反馈候选，`start` 才揭示共同起点性能；Agent 通过现有 step/finish 命令逐轮探索；全部关闭后 `compare` 运行对照，最后执行精确枚举。

已完成的 [Agent V2 实验报告](../results/agent_v2_pilot/report.md)包含 5 条轨迹、曲线、45 个运行的完整记录及复现说明。此试验的 720 排列空间是人为缩小的子空间，不是完整 DSL 的最优性证明。V1 自动生成负载的接口仍保留原来的变体评价行为，不能将两种 `finish` 混为一谈。

## Agent V3：独立上下文与提示/反馈对照

V3 使用新接口 `python -m hbm_toy.agent_v3`，保留原 V2 代码与冻结归档。四个条件为 `old_summary`、`new_summary`、`old_phase`、`new_phase`，分别组合原/新提示与汇总/分批反馈。每条件使用一个不继承母对话的模型上下文，各自完成三条任务；同一条件内的任务共享上下文，不能视作完全独立的模型重复运行。

```powershell
python -m hbm_toy.agent_v3 prepare --folder results/run_v3_new
# 查看 inputs/，在 one_shot/ 中为每任务写入 18 份不重复提案；此时未运行性能评价。
python -m hbm_toy.agent_v3 start --folder results/run_v3_new
# 将每组独立上下文指向自己的 briefings/<条件>.json 与 sessions/<条件>/。
python -m hbm_toy.agent_v3 step --folder results/run_v3_new/sessions/new_phase/N01_burst --proposal examples/proposal.json
python -m hbm_toy.agent_v3 finish --folder results/run_v3_new/sessions/new_phase/N01_burst --note "记录停止原因"
# 全部 12 个会话结束后，才允许运行普通对照与精确参照。
python -m hbm_toy.agent_v3 compare --folder results/run_v3_new
```

提案仍需 `hypothesis`、`expected`、`dsl`；示例命令中的提案仅展示格式，不保证适合任务。输入文件包含 activity/joint 启发式 DSL，模型可自行选择是否评价。每会话共同起点占两次预算，总上限 20 次实际后端调用；缓存不重复计数，非法提案不计数，执行失败计数。

`phase` 组从**同一次连续模拟**的事件中提取前/后批次的平均延迟、排队、行状态和最后完成时刻，不在分界处重置队列。`summary` 组不收到这些字段；所有组仍能读取同一原始轨迹、静态统计及预先指定的分界。增加反馈不额外执行模拟器，但可能增加日志处理和模型阅读成本。各批最后完成时刻不能相加。

源码、提示、简报、输入及无反馈提案均有冻结检查。V3 的 JSON 承诺使用规范化内容哈希，文本源码哈希按统一换行读取，跨平台换行不会改变承诺。不同上下文的读文件范围通过实验指令约束，**不是文件系统级隔离**。查看本条件以外的反馈或事先调用模拟器，会破坏实验约定。

`prepare` 生成的是固定三条任务；重复执行只能复测，不能获得新的未见任务。更换任务生成器应建立新的实验版本。当前对话额外提交的无反馈批次带有旧实验背景，作为补充参考，不能当作四个独立模型上下文各自的严格消融。

`examples/agent_v3_prompt.md` 标题中的“下一版”“尚未验证”是冻结时的原文，该提示已用于上述 V3。不要为更新研究表述改动它。新的“强搜索/一次生成/逐轮无新反馈/逐轮反馈”对照仅是[协议建议](RESEARCH_POSITIONING.md#next-agent-study)，不是这个命令的四组条件；旧共同起点和预算契约也不随建议改变。

完成后的候选重放及曲线生成：

```powershell
python -m hbm_toy.agent_v3_report replay results/agent_v3_pilot
python -m hbm_toy.agent_v3_report render results/agent_v3_pilot
```

## DSL 与地址语义

首次接触地址位操作，先看根目录的 [DSL 入门教程](../DSL_TUTORIAL.md)：从字节地址、块编号和字段拆分讲起，用具体数值演示交换、异或及组合顺序，并区分负载、布局、硬件配置与映射策略。本节维护运行契约。

DSL 是 Domain-Specific Language（领域专用语言），针对特定问题提供表达规则，可以处于不同抽象层次。SQL、正则表达式都是例子。[概念介绍](https://martinfowler.com/bliki/DslQandA.html)

本项目用可组合的原语表达策略：原语规定能做什么，语法规定如何组合，语义规定执行顺序，约束规定合法范围和无别名要求。JSON 只是书写格式；第一版不另造文本语法，也不局限于从几种完整预设方案中选择。

| 原语 | 语义 |
| --- | --- |
| `swap_bits(a, b)` | 交换两个地址比特 |
| `xor_bit(dst, src)` | 执行 `bit[dst] ^= bit[src]`，要求两个位置不同 |

直接传给 `evaluate` 的输入是 DSL 对象，模型提案则在外层加 `hypothesis`、`expected`、`dsl`。例如：

```json
{
  "version": 0,
  "operations": [
    {"op": "xor_bit", "dst": 0, "src": 6},
    {"op": "xor_bit", "dst": 1, "src": 7}
  ]
}
```

默认地址容量是 4 MiB：64 字节粒度 × 2^16 个块。**这些数字是玩具参数，不对应一款真实 HBM。**

| 变换后的块地址位 | 字段 |
| --- | --- |
| 0–1 | channel：4 个 |
| 2–3 | bank：每个 channel 4 个 |
| 4–7 | column：每行 16 个粒度 |
| 8–15 | row：每个 bank 256 行 |

先从字节地址分离块编号 `address // 64` 和粒度内偏移 `address % 64`，再按数组顺序变换块编号，最后完整、无重叠地切出各字段。比特从最低位 0 开始，后续操作读取前一步结果，偏移保持不变。默认最多 8 个操作，位编号必须不同且在 0–15 内；空序列为 identity。

访问粒度、位宽、字段拆分与容量属于固定配置，候选不能自行修改。每个原语自身可逆，反向执行原序列即可求逆；当前使用匹配完整二进制地址域的二次幂容量，避免额外范围处理。编译器还会构造 GF(2) 矩阵并检查满秩，解释器、编译结果和逆变换另做抽样/边界交叉检查。这支持固定地址域的无别名判断，不能替代 RTL 生成器检查或完整控制器正确性证明。

### 一个地址交织示例

仅为演示，使用 8 位块编号：第 0–1 位选择 channel，第 2–3 位选择 bank，第 4–5 位选择 column，第 6–7 位选择 row。执行上述两次 XOR 后：

| 块编号 | 不变换时的 channel | 执行示例 DSL 后的 channel |
| --- | --- | --- |
| 0 | 0 | 0 |
| 64 | 0 | 1 |
| 128 | 0 | 2 |
| 192 | 0 | 3 |

原本集中在同一 channel 的请求被分散。表格只是地址运算结果，是否加速仍取决于并发、行局部性和其他瓶颈；这个缩小地址域的例子也不替代上面的默认配置。

### 配置与探索边界

可使用部分配置覆盖默认值，参数名见 [Config](../hbm_toy/model.py)：

```json
{"queue_depth": 8, "t_activate": 12, "max_operations": 8}
```

保存为 `my_config.json` 后，把全局选项放在子命令前：

```powershell
python -m hbm_toy --config my_config.json evaluate examples/identity.json --workload stride
```

session 一旦创建，后续命令使用 `state.json` 中的配置，不应编辑进行中的状态来改变比较条件。

这两个原语表达 GF(2) 上的可逆线性变换，操作数上限进一步限制空间；它们不能表达任意非线性映射、数据布局或运行状态相关策略。同一 DSL 经确定性编译生成软件映射和 RTL 映射，二者应共享精确含义。

现有实验只组合已有原语，保持解释器、负载与评价规则固定。以后 Agent 可以提出新原语，但需同时定义语义、实现、后端支持和验证方法，经独立检查纳入新 DSL 版本。布局分块、维度置换、介质放置或调度原语均适用此规则；扩展空间后的成绩不能直接与较小空间混为一谈。未来静态布局与生命周期状态的分层原则见[研究定位](RESEARCH_POSITIONING.md#dsl-design-principles)，不是在当前位变换 JSON 中任意增加字段就能实现。

## 访问流和时序模型

默认每条请求为一个对齐的 64 字节粒度，大小隐含在配置中；包括唯一 ID、物理字节地址、计划到达时间、读写类型和分析用 stream 标签。跨粒度请求拆分留待扩展。映射只读地址与固定配置，不读 stream、token 或 head 标签。

请求直接进入内存系统边界，计划到达时间预先给定，不随推理计算进度改变；当前不建模缓存过滤、计算执行及完整推理依赖。

默认每条访问流 768 次请求，每周期计划到达 8 次，每 16 次请求中有一次写。读写目前使用相同时延。

| 名称 | 训练访问流的块编号 | 搜索结束后使用的变体 |
| --- | --- | --- |
| sequential | `i` | 起点增加 32 |
| stride | `i * 64` | `i * 96 + 16` |
| kv_interleaved | 8 条流交错，`lane * 4096 + (token % 256) * 16` | 6 条流，间距 3072，token 步长 24 |
| random | 均匀随机块地址 | 不同随机种子 |

所有块编号按固定容量取模。`kv_interleaved` 仅模拟规律性的多流间隔；不含真实 attention kernel、页表或 KV cache 管理实现。变体是人为构造的分布变化测试，不是大规模真实泛化基准。

模型采用事件推进，不逐个模拟 DRAM 命令周期：

- 每个 channel 有容量 16 的 FCFS 待发队列；队满时请求留在上游，按原次序补入。按计划到达时间、ID 排序。
- 每个 channel 最快每周期发出一个请求。队首等待目标 bank 可用，其他 bank 的请求不能越过它。
- bank 从请求发出到数据传输完成均被占用。行命中准备时间为 4；空行加激活 8；行冲突再加预充电 8。
- 不同 bank 的准备可重叠；同一 channel 的传输总线每次占用 4 周期，按发出顺序预约。不同 channel 独立运行。
- 请求延迟从计划到达到完成，包含上游背压。完成时间从最早计划到达到最后一条完成，必须排空全部请求。

指标包括完成周期数、平均/p95 延迟、行命中/冲突率、channel/bank 请求数、总线占用比例，以及上游与控制器等待时间。比较时固定初始空行/队列、注入规则和统计范围；完成周期数定义为最后请求完成时刻减去最早计划到达时刻。行命中率是诊断指标，排名只按完成周期数。

未建模 bank group、pseudo-channel、refresh、真实读写切换、完整 JEDEC 时序、缓存/计算依赖和互连。这是可解释的抽象模型，不是 Ramulator 替代品；例如银行占用和按序预约总线会限制实际硬件可能实现的重叠。

## 对照与预算

| 搜索器 | 实现 |
| --- | --- |
| random | 共用起点后随机生成操作组合 |
| local | 对当前最佳做插入、替换或删除；定期随机尝试 |
| activity_local | 先按地址位翻转率把活跃位放入 channel/bank，再局部搜索 |
| packed_local | 进一步把活跃位安排到 column，再局部搜索 |
| llm_file_bridge | 外部语言模型读取反馈并通过文件提交候选 |

前四种均是普通算法。位活动启发式不是 DReAM/PAE/Flatfish 的复现。`packed_local` 是看到首轮 Agent 改善方式后增加的事后诊断基线，不能据此宣称做完了预先注册的公平竞赛。

每次搜索最多 20 次实际性能后端评价，共用的 identity 和 row-XOR 起点也计入。规范化矩阵、配置、访问流哈希与后端版本共同构成缓存键；等价重复候选不重复调用，日志记录缓存状态。文件协议限制最多 `10 × budget` 条记录，普通搜索限制最多 `30 × budget` 次提案尝试；小搜索空间可能提前停止，实际调用数以日志为准。

搜索后的候选及 identity 变体评价另外记 2 次，不参与搜索；benchmark 的静态基线表也有单独评价成本。RTL 调用另计。当前同步玩具后端遇到内部异常会终止实验，尚未实现远程任务超时、重试或失败费用审计。

随机种子 0、1、2 改变搜索过程；各方法使用相同的训练访问流。三次搜索不足以建立统计显著性。候选和指标可以重放，模型是否会重新生成同一序列不保证。

## RTL 分支

本节描述旧地址映射模块的导出与检查。未来是否需要 RTL 由改变的组件决定：软件布局/分配优先验证数据内容、引用和状态；改变硬件译码或控制器时再验证对应 RTL。器件模型检查 DRAM 命令合法、控制器 RTL 对照和 KV 内容验证覆盖不同性质，不能互相替代；依据见[验证层次](RESEARCH_NOTES.md#verification-layers)。

RTL 是 Register Transfer Level，即寄存器传输级，使用寄存器与组合逻辑等描述数字电路，通常写成 Verilog、SystemVerilog 或 VHDL。可综合的描述可进一步转换为电路实现。[Yosys 的 RTL 介绍](https://yosyshq.readthedocs.io/projects/yosys/en/v0.65/appendix/primer.html)

本项目最初只生成一个地址映射模块：输入物理地址，输出 channel、bank、row、column 等字段。这个模块可以是没有寄存器的纯组合逻辑，不包含完整内存控制器或 HBM 存储单元。

| 分支或步骤 | 回答的问题 | 主要产物 |
| --- | --- | --- |
| Ramulator 性能评价 | 使用该策略时，内存系统处理访问流的表现怎样？ | 完成周期数、访问延迟、行命中率等 |
| RTL 功能仿真或形式验证 | 硬件实现是否符合策略规定？ | 检查范围内的通过或失败、反例、覆盖范围或证明状态 |
| 综合与时序等分析，后续扩展 | 实现需要多少硬件资源，能否满足时钟要求？ | 逻辑资源统计、在给定目标与约束下的面积和时序估计 |

验证约定如下；当前实现的执行状态见本节末尾：

1. 检查 DSL 的地址范围、映射无别名和可逆性。
2. 通过参考模型获得预期输出，并从 DSL 生成 RTL 地址映射模块。
3. 用 testbench（测试平台）提供输入地址，运行 RTL 仿真，比较实际输出与预期输出。
4. 保存差异输入、预期与实际输出、工具版本和验证覆盖范围，供子 Agent 分析。

缩小地址域时可进行穷举检查；较大地址域可以先做抽样与边界测试，后续根据需要加入形式验证。Icarus Verilog 可编译设计与测试平台并运行仿真。[Icarus 仿真说明](https://steveicarus.github.io/iverilog/usage/simulation.html)

应记录检查方法与覆盖范围。抽样测试通过不能当作完整地址空间的正确性证明；共享编译层也可能引入共同错误，因此参考检查应包含独立的预期样例或数学性质检查。

RTL 功能验证通过只说明已检查范围内的映射行为符合预期。面积、频率和功耗需要额外的综合、目标器件或工艺库、约束及分析流程，不能从功能仿真通过直接推断。若硬件实现需要额外流水级，其延迟与吞吐影响也应反馈到性能评价中。

对第一版少量交换与 XOR 原语，RTL 分支主要用于检查生成实现的正确性。代码生成和工具执行可由普通程序完成；子 Agent 的预期价值在于分析失败、提出针对性测试和归纳实现约束，其增益仍需实验判断。该分支分阶段接入，不阻塞最小性能探索闭环。

### 导出与当前状态

```powershell
python -m hbm_toy export-rtl results/agent_kv_v1/best_policy.json --output results/my_rtl
```

生成 `address_mapper.sv`、`tb.sv`、`vectors.mem` 和 `verification.json`。模块输入完整字节地址，输出 channel、bank、row、column 和 byte_offset。期望值由顺序解释器产生，RTL 由矩阵表达式产生。默认生成 2071 个边界/随机地址向量；小地址域支持穷举。

若 PATH 中存在 `iverilog` 和 `vvp`，命令会自动编译并仿真，记录输出和状态。本机缺少这两个工具，已生成文件，状态明确为 **`not_run`**。未做 RTL 仿真、综合或时序/功耗分析；Python 检查通过不代表 RTL 验证通过。无需为运行 Python 玩具先安装硬件工具。

<a id="architecture"></a>
## 目标架构与后端契约

[README 流程图](../README.md#总体流程目标架构) 分为策略探索、性能评估、按需验证和反馈迭代。母 Agent 决定任务；确定性程序校验、编译候选后分派给子 Agent。性能评估子 Agent 负责评估任务的准备、执行组织和结果分析，任务前端与仿真器是它调用的工具；验证子 Agent 同样组织适用的检查。标注“调用”的箭头由子 Agent 指向工具，工具再将结果返回子 Agent 分析。

当前性能/RTL 模块是确定性工具，没有独立评估或验证子 Agent；V3 的独立模型上下文是实验条件隔离，不是这两个角色的实现。未来角色可以使用同一个模型、分别维护上下文，无需不同机器或常驻进程。

<a id="agent-execution-modes"></a>
### 单对话与独立子 Agent 的区别

“母 Agent / 性能评估 / 验证”首先是职责划分，实现时可以由一个对话兼任，也可以拆分。当前由对话综合承担策略提出、工具调用和结果解释；Python 模块执行固定的解析、模拟、检查和记录。没有分别建立性能或验证角色的任务上下文与自主调用循环，因此称为“单对话加工具”，而不是已经完成母子 Agent 架构。尤其 RTL 尚未实际仿真，不能说当前对话已经完成了全部验证职责。

| 方面 | 单对话兼任，当前方式 | 拆成独立子 Agent，目标选项 |
| --- | --- | --- |
| 模型与上下文 | 一个对话综合处理任务及工具结果 | 可用同一个模型，但每个执行单元维护自己的任务输入和后续上下文 |
| 决策与调用 | 当前对话决定候选、调用工具、解释反馈 | 母 Agent 委派任务；子 Agent 在给定候选和预算内自行组织工具调用、诊断和报告 |
| 信息传递 | 结果进入同一对话，交接少，但内容会累积 | 可限定子 Agent 所见信息，母 Agent 接收摘要及原始证据引用；有遗漏信息或摘要失真的风险 |
| 并行与责任 | 也能并行调用工具；分析职责在同一对话内 | 不同任务可独立推进、记录状态和归属；同一模型的多个上下文仍可能犯相关错误 |
| 成本与适用性 | 简单任务开销低、理解全局方便 | 复杂日志、专项诊断或验证任务可能受益，但增加模型调用、协调及上下文传递成本 |

这里的“独立”指任务状态和执行上下文可区分，不保证文件权限或信息严格隔离；需要这样的隔离时必须由执行环境落实。使用相同模型、同一台机器，甚至由母对话临时委派，都可以实现这种分工；不要求用户手动打开多个聊天窗口。反之，在一个对话中轮流写“现在是性能 Agent”只是在切换角色，不会自动产生独立上下文。

例如，同一候选性能退化时，单对话可直接检查分批统计再决定下一步；拆分后，性能子 Agent 接收候选与诊断额度，调用统计/仿真工具区分排队或布局代价，返回有证据的判断，母 Agent 再决定如何修改策略。候选修改权和总体预算仍归母 Agent；子 Agent 的补测计入共享预算。两种组织方式都能完成该任务，拆分的价值在于是否提高质量、节省总时间或使任务管理更清楚，需要同工具、同信息条件和明确资源口径下的对照。

### 组件职责与执行契约

| 组件 | 职责 |
| --- | --- |
| 母 Agent | 收集访问特征、分析历史、提出假设与 DSL、分派任务和预算 |
| 传统搜索工具，后续可选 | 根据结构建议与历史探索变体，返回候选 |
| DSL 检查与编译层 | 检查合法性，生成各后端语义一致的表示 |
| 任务前端，按所选系统问题开发 | 从固定逻辑操作、依赖与候选策略生成请求、分配和转换事件；固定流量任务可使用现有轨迹 |
| 语义与状态检查 | 用独立参考模型验证数据位置、内容与生命周期；当前实现仅覆盖地址变换检查 |
| 性能评估子 Agent，待实现 | 接收母 Agent 的候选与预算，准备输入并调用任务前端/性能后端，检查执行状态、分析瓶颈、在授权预算内组织诊断并返回报告 |
| 验证子 Agent，待实现 | 接收验证任务并调用适用工具、定位反例；涉及硬件时组织 RTL 检查及必要的综合/时序分析，返回覆盖范围和实现成本 |
| 实验记录模块 | 保存候选、配置、版本、原始结果，复用相同实验结果 |

性能与适用的验证分支可并行，分析子 Agent 可按任务启用，不以两个角色固定齐备作为闭环验收条件。候选绑定逻辑负载、硬件配置、前端、工具版本与实验标识；反馈按这些信息汇总。DSL、数据语义和编译产物须一致；若验证发现实现需要额外流水级或缓冲资源，必须将其成本送回性能模型后再评价。

**现有代码的实际调用链。** 固定轨迹的 `session-step` 经 [`trace_bridge.submit`](../hbm_toy/trace_bridge.py) 解析候选并校验空间，再调用 [`Evaluator.evaluate`](../hbm_toy/experiment.py)。评价器检查缓存与映射合法性，未命中缓存时执行 `simulate`；接口随后更新预算、历史及 `feedback.json`，由当前对话读取。合成负载的 `session_step` 使用同一个评价器。独立的 [`ramulator_backend.run`](../hbm_toy/ramulator_backend.py) 通过子进程调用 C++ 驱动并校验结果，没有在运行前后调用语言模型，也未接入会话评价器。因此，本次澄清的是目标图的职责表达，无需据此改变现有模拟器或冻结实验。

评价期间候选保持不变；子 Agent 的修改建议应形成新候选。工具修复后记录新版本并重新评价，不混合不同实现版本的结果。更换 Ramulator 后端时同样固定版本、配置与注入方式，并重新比较候选排序。

母 Agent 每次先保存瓶颈假设、原语修改和指标预测，再下发评估任务；当前最小实现由对话直接调用评价器。未来子 Agent 应先核对任务与预算，再组织工具执行；失败时报告状态与原因，不把未执行检查当作通过。反馈区分工具事实（完成时间、冲突数、退出状态、反例）与 Agent 解读（可能原因和后续建议），解读需关联证据。每份反馈应能追溯候选、配置、版本和原始日志；诊断实验另建记录。

执行状态与正确性状态分别记录；非法提案、运行失败和未执行验证不能当作正常成绩，未执行标为 `not_run`。本节是完整目标契约，当前文件协议及异常处理的实际范围以本指南前面的说明为准。

## 后续系统模型的开发契约

以下是文献精读形成的设计要求，尚未实现为新接口；具体子问题先按[任务规格](RESEARCH_POSITIONING.md#minimal-system-task)选择。旧命令与结果继续使用前文约定。

| 层次 | 开发时应明确的语义 | 必须避免的错误归因 |
| --- | --- | --- |
| 固定任务 | 对象、逻辑操作、到达/计算规则、容量、合法权限与主要目标 | 候选改变工作量、数据精度或硬件资源而未计成本 |
| 策略与状态 | 元素到字节布局、对象范围；仅在需要时加入 partial/full、暂存、提交、共享/回收 | 每个局部映射可逆，就默认所有对象和状态全局正确 |
| 访问生成 | 静态映射固定请求；依赖任务由前驱完成产生后续 ready；分配任务生成自身流量 | 将一份最终物理轨迹用于会改变分配、eviction/recompute 的所有策略 |
| 转换与容量 | 未满块的读写、临时副本、预留目标、搬移流量和元数据 | 只计算写入加速，漏掉读取、容量及转换成本 |
| 计时与评价 | 定义 ready、accepted、completed；分别定义读写完成，核对时间单位与目标范围 | 将反压视为计算依赖，将写接受当作写可见，将后端驻留当作纯器件延迟 |
| 正确性 | 内容参考、写后读、对象隔离、共享引用、提交发布顺序及适用的数值检查 | 用 RTL 通过替代数据语义，用时序合法替代目标控制器校准 |
| 搜索与记录 | 任务/策略/前端/后端版本和摘要共同标识评价；真实调用、提案、诊断及模型成本分账 | 免费隐藏初始化/恢复评价，或把更多原语和信息的收益归给 Agent |

来自[PFM/PATTON](RESEARCH_NOTES.md#kv-research-scope)的原则是保留真实冲突和可摊销转换；来自[Ramulator/DRAMSys4](RESEARCH_NOTES.md#backend-contract)的原则是让模型覆盖所声称的效果。先用手算例子和参考执行核验机制，再增加后端细节。旧玩具 FCFS 与未来 FRFCFS 等后端存在控制机制差异，应比较固定候选的排序、选中策略损失及原因，不只对齐平均周期数。

新 DSL 需要三种不同检查：表达语义是否正确；行为在目标权限下是否可实现；收益是否在完整成本下成立。Agent 可提出组合或新原语的建议，但不能在冻结实验期间修改正确性判定或计分规则。结构化数学工具、现有机制及能跨局部障碍的搜索方法应在同一合法空间中参与比较。
