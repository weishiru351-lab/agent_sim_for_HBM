# 研究定位：Agent 主导探索，以公平实验检验能力

更新日期：2026-10-08。论文说明、发表状态和已核验入口统一见 [文献阅读指南](LITERATURE_GUIDE.md)；本文只讨论这些证据对本项目的影响。

## 已知什么，还缺什么

**负载相关地址映射是实际问题，但有价值的研究问题需要进一步收窄。**

| 已有证据 | 对本项目的影响 |
| --- | --- |
| [R01 Shuhai](LITERATURE_GUIDE.md#r01) 展示真实 HBM 的映射敏感性，其测试中的默认映射也表现很好 | 必须分别测量“避免坏映射”和“超过合理默认方案”的收益 |
| [R02 SDAM](LITERATURE_GUIDE.md#r02) 已按数据结构选择映射；[R03 Flatfish](LITERATURE_GUIDE.md#r03) 已研究学习生成映射 | 按负载适配或引入学习方法本身不足以说明创新；Flatfish 正式全文已取得，方法与实验仍待精读 |
| [R04 XOR 数学模型](LITERATURE_GUIDE.md#r04)、[R08 PAE](LITERATURE_GUIDE.md#r08) 提供结构化优化方法 | 强数学方法与领域启发式应进入对照，不能只比较随机搜索 |
| [R05 AgentDSE](LITERATURE_GUIDE.md#r05)、[R06 ArchEval](LITERATURE_GUIDE.md#r06) 已研究 Agent 与体系结构评价工具的协作 | 文件接口和反馈循环已有先例；需要具体问题或机制上的新增贡献 |

尚缺的关键证据是：**真实 KV 请求流在选定平台上，相比合理默认策略和强基线，是否还有稳定且值得付出搜索成本的收益。** 当前玩具只证明流程能运行、映射会影响模型结果；简单启发式已追平那次 Agent 结果，不能据此判断真实 HBM 优势或 Agent 优势。

## 两条平台路线

平台暂不限定，先比较实际自由度。下表是基于文献与当前项目状态的研究建议。

| 维度 | 路线 A：可修改控制器/定制硬件 | 路线 B：现有 GPU 推理软件 |
| --- | --- | --- |
| 优化对象 | 物理地址到 channel、bank、row 等位置的映射，必要时与布局协同 | KV 布局、分块、分配、页管理及访问组织 |
| 可控制范围 | 以明确的架构和 IP 约束为边界，定义位选择与 XOR 组合 | 以设备、驱动和框架已开放接口为边界 |
| 关键相关工作 | [SDAM](LITERATURE_GUIDE.md#r02)、[Flatfish](LITERATURE_GUIDE.md#r03)、[XOR 数学模型](LITERATURE_GUIDE.md#r04)；扩展到 PIM 时补读 [PFM](LITERATURE_GUIDE.md#r14) 与 [PATTON](LITERATURE_GUIDE.md#r15) | [PagedAttention](LITERATURE_GUIDE.md#r12) 与 [vAttention](LITERATURE_GUIDE.md#r13) |
| 评价方式 | DRAM 时序仿真及可信请求模型；必要时加入系统仿真、RTL 综合/验证或原型 | GPU 实测、系统剖析与端到端推理评价 |
| 主要难点 | 请求流真实性、映射与调度耦合、实现成本、切换时的数据一致性 | 区分缓存、合并访问、kernel 与分配收益；既有系统基线很强 |
| 有价值的产物 | 可实现的映射机制、跨负载规律、低成本适配方法 | 可部署的数据组织与分配方法，以及完整开销下的收益 |
| 与当前玩具的距离 | 接口相近，但时序真实性与硬件约束尚需补齐 | 需要调整 DSL 层级及评价边界，当前位映射 DSL 不能直接部署 |
| 适合的团队资源 | 控制器、RTL、体系结构或仿真经验 | GPU、推理框架与 kernel 开发经验 |

现有 GPU 的虚拟内存/分配控制能力不能直接视为可重编程的 HBM bank 映射。定制 NPU/PIM 的设计也不能直接作为普通 GPU 的能力证明。具体 IP 的限制见 [厂商资料](LITERATURE_GUIDE.md#vendor-docs)。

分析 KV 问题时，沿着下面的因果链检查，而不是从张量形式不同直接跳到映射需求不同：

```text
KV 结构与数据布局
    → kernel 访问顺序与分配
    → 缓存、请求合并、地址转换
    → 到达控制器的请求流
    → 地址映射与调度
    → 介质执行和最终性能
```

## 研究主线与支线

**项目主线已明确为 Agent 主导内存策略探索。** 研究目标是在复杂负载、组合设计空间和有限评价预算下，检验 Agent 能否通过负载理解、假设提出、实验规划与反馈修正，得到更好的可实现策略，或以更少的昂贵评价达到相当的质量。这是待验证的研究假设，当前玩具尚未建立比较优势。

“Agent 是主力”指优化过程中的候选构造、探索方向、工具选择和预算分配由 Agent 主导。数值计算、局部搜索、仿真与正确性检查由确定性工具完成；部署后的地址变换仍由软件或硬件执行。

| 贡献层次 | 需要证明什么 | Agent 的位置 |
| --- | --- | --- |
| 主线：Agent 探索方法与能力 | 具体的候选生成、诊断或实验规划机制在公平条件下相对强搜索器和通用 Agent 循环的增益 | 持续主导探索，是主要研究对象；需要消融、成本统计和泛化评价 |
| 支线：规则发现与固化 | 将探索经验转成可复用启发式，说明适用范围、失效边界和复用成本 | 发现与修正规则，并可将规则作为后续探索工具 |
| 支线：内存机制 | 找到真实瓶颈，提出相对已有机制有增量、可实现且可复用的策略 | 在主线探索中产出有价值的内存策略 |
| 支撑：测量与基准 | 明确真实请求的映射敏感性与优化余量，提供有代表性、可复现的评价任务 | 利用可信任务与工具评价其探索能力 |

真实内存问题的表征与收益空间确认，是主线实验成立的前提。研究目标保持 Agent 主导，但结论必须由证据决定；若某类任务被简单算法充分解决，应保留该结果，检查任务范围和方法机制。[ArchGym](LITERATURE_GUIDE.md#r09) 可帮助设计搜索对照；[AlphaEvolve](LITERATURE_GUIDE.md#r16) 和 [LLAMBO](LITERATURE_GUIDE.md#r17) 提供搜索组织方式的启发，但不能替代直接相关工作的比较。

## Agent 的定位与搜索方法

本项目将 Agent 定位为**利用领域知识持续主导探索决策的主体**。它结合访问步长、地址字段和冲突统计提出结构性修改，自主决定下一步验证什么、调用什么工具以及何时调整假设；最终性能与正确性由工具评价。

传统优化方法也能避免穷举。例如，局部搜索修改已有候选的邻近策略，进化算法维护候选群体并产生变体，贝叶斯优化根据历史观测预测哪些候选值得评价。Agent 的收益需要与这些方法比较，不能仅通过胜过随机搜索就认定其全面优越。

建议逐步探索以下分工：

| 组件 | 在搜索中的职责 |
| --- | --- |
| Agent | 提出瓶颈假设与候选结构，决定跨多个操作的修改、诊断实验、工具调用及评价预算分配 |
| 传统搜索工具，后续可选 | 在 Agent 选定的范围与预算内探索局部变体、维护候选多样性或建议下一批候选 |
| 确定性检查与评价工具 | 检查合法性和正确性，测量性能并保存证据 |

例如，Agent 发现固定步长使 channel 选择位不变化，可以建议把特定高位混入低位；搜索器再探索混入哪些位、如何组合操作。掌握同样规律的专用启发式也可能做到，因此实验需要检验 Agent 在不同负载上的适应能力与额外成本。

对混合方法保持有条件的乐观，以下是待验证的预期：

| 场景 | 预期与限制 |
| --- | --- |
| 少量固定参数、后端很快、只有单一分数反馈 | 传统搜索可能更高效，模型调用成本可能占主导 |
| 较长的操作组合，且能提供访问特征和瓶颈信息 | Agent 可能提出更有依据的结构性修改 |
| 跨负载归纳规律或提出扩展原语 | 值得探索，但验证难度和错误风险也随表达能力增加 |

最小版本先完成母 Agent 的反馈循环与基线比较。混合搜索是后续可选路线，不要求同时实现所有算法；贝叶斯优化等方法需要为离散、可能变长的 DSL 设计合适的编码和候选生成方式。

有限预算内通常只能报告“目前找到的最佳候选”。“局部最优”要求先定义策略邻域，并确认邻域中没有更好的合法候选；不能仅凭若干轮未改善就作出这一结论。

### 支线：Agent 帮助发现可固化的规则

**Agent 帮助发现了一个可以固化的规则。规则一旦写出来，执行它当然可以比重新推理更便宜。这本身可能是 Agent 的一种有价值的定位。**

本项目保留这一认识作为支线贡献。规则可以成为 Agent 调用的工具、后续实验的强基线或最终策略的低成本实现；主线仍需直接检验 Agent 持续探索的能力。

这一认识来自首轮实验：观察到 Agent 对 column 排布的改善后，我们把其中的规律提炼为确定性启发式，后者也达到了相同成绩。因此，最终规则能被简单程序执行，并不抹去 Agent 在发现过程中的潜在贡献；也不意味着每次选择策略都必须调用 Agent。具体过程与事后补充基线的限制见 [实验解读](INITIAL_RESULTS.md#agent-rule-discovery)。

主线与支线应分别评价：

| 目标 | 主要产物 | 评价重点 |
| --- | --- | --- |
| 主线：Agent 主导策略探索 | 多轮诊断、实验决策与给定负载下的具体 DSL 候选 | 同等信息和预算下的策略性能、评价次数、总成本，以及移除 Agent 决策后的变化 |
| 支线：规则发现与固化 | 根据负载特征生成策略的可复用启发式，以及适用条件 | 冻结规则后在未见负载上的收益、失效边界，以及发现与验证的总成本 |

后一种路径可以是：**Agent 提出瓶颈假设 → 工具实验验证 → 提炼并实现确定性规则 → 在未参与规则设计的负载上检验 → 重复使用规则。** Agent 主要参与规则的发现和修订，日常策略生成可以由普通程序完成。评价时应分别记录一次性的发现成本与每次应用规则的成本，不能只报告固化后的低开销。

当前实验只提供了这种工作方式的一个例子，尚未证明规则的新颖性、跨负载有效性，或 Agent 比人工设计及其他规则搜索方法更高效。后续应保留规则的发现过程、适用条件和反例，并与已有领域启发式比较；这类产物补充主线贡献，主线的 Agent 搜索能力仍需独立评价。

后续已完成一次 [规则发现诊断实验](../results/rule_study_v1/report.md)：冻结旧启发式，在六位地址空间中用联合统计修复相关位造成的资源闲置，并枚举全部 720 种位排列作为参照。新规则在两个发现样例上达到排列空间最优，但验证暴露了退化：只统计 bank 内单个位翻转，仍会遗漏多个 row 位同时变化的影响。这为下一轮提出了更具体的规则假设，也说明“固化规则”应同时固化适用条件与反例，不能只保存成功案例。

## 值得检验的假设

以下是候选研究问题，尚未证实其新颖性或收益。

1. **不同 KV 数据是否需要不同策略？** 比较 K/V、精度、元数据、上下文长度与批次的请求特征，先确认差异是否到达介质请求层，再考虑按区域配置。
2. **单负载最优策略是否脆弱？** 在未参与搜索的模型、布局和负载上，比较平均性能、尾部性能和最差退化，研究稳健策略。
3. **布局与映射是否需要联合优化？** 比较分别优化、顺序优化与联合优化，完整计入 padding、迁移、元数据和访问成本；PIM 路线需补查 [UMDAM 正式版本](LITERATURE_GUIDE.md#r20)。
4. **诊断证据是否减少昂贵评价？** 比较只读分数、读取相同统计的启发式、通用 Agent 与候选方法。解释文本本身不能证明有效推理。

初期优先离线搜索或部署前选择策略。运行时可执行小型确定性规则；动态改写已有数据的映射则需另行解决迁移、一致性和切换代价。

## 进入下一阶段的最低证据

先做一组小而可信的比较：**代表性真实请求 × 合理默认方案 × 强启发式/优化器 × 搜索所得策略**。搜索负载与最终评价负载分开，固定平台、合法空间、反馈信息和预算，同时记录后端调用与模型推理的总成本。

- 若只比刻意构造的坏映射好，先补齐默认方案与强基线。
- 若真实请求对映射不敏感，研究其原因，或调整到布局/分配层。
- 若优化余量存在但简单算法已经解决，说明该任务尚不能支持 Agent 优势；保留负结果，检查有实际依据的负载结构与方法改进，避免只挑有利样例。
- 若相同信息与成本条件下，Agent 在多个未见任务上持续带来增益，再据此支持 Agent 主导探索的主线结论。

当前未完成的证据包括：Flatfish 和 UMDAM 正式全文复核、目标平台接口确认、真实 KV 请求数据及新一轮强基线比较。接入 Ramulator 可以提高评价真实性，但不能单独补齐这些研究证据。


## 如何评价 Agent 的贡献

以下是后续扩展实验的设计要求；当前玩具已实现的预算与异常处理范围见 [运行指南](TOY_GUIDE.md)。

主指标使用**固定访问任务的完成时间**。行命中率、负载均衡程度等作为诊断信息，不能单独替代最终目标。

先完成手工基线、随机搜索与反馈驱动的 Agent 比较，再逐步补充下列对照：

| 方法 | 用途 |
| --- | --- |
| 手工基线，如不进行地址变换 | 提供可解释的起点 |
| 随机搜索 | 检查 Agent 是否优于相同空间内的随机尝试 |
| 简单局部搜索 | 检查基于小幅修改的常规搜索能取得什么效果 |
| 位活动及 column 排布启发式，已实现 | 检查掌握简单地址规律的程序能取得什么效果；后者为首轮后的补充对照 |
| 进化搜索或适配后的贝叶斯优化，后续加入 | 与有竞争力的传统搜索方法比较 |
| 模型一次性提出一批候选，不读取评价反馈 | 观察模型已有知识能提供多少帮助 |
| 母 Agent 根据反馈逐轮提出候选 | 检查反馈循环的增益 |
| 母 Agent 加两个子 Agent 的分析 | 检查分工是否在额外调用成本之外带来收益 |
| 同一搜索器加入或移除 Agent 候选建议 | 检查混合方法中 Agent 的额外贡献 |
| 相同工具由固定流程调用，或由 Agent 自主调用 | 检查实验选择与预算分配的收益，避免把工具本身的能力归给 Agent |

预算可以从每种搜索方法最多 20 次后端评价开始，这只是实验起点。建议将一次性能评价定义为一个候选在一个固定工作负载、配置和后端上的执行；同一候选跑多个工作负载应分别计数。RTL 验证调用单独记录。

公平比较需要保持工作负载、合法策略空间、初始条件与预算口径一致，并约定多工作负载结果的汇总方法。失败的后端执行也计入调用预算；非法提案、重复提案、缓存命中和实际执行分别记录，并设置提案数或总时间上限，避免无限重试。

同时记录各方法可获得的负载特征与反馈信息。如果 Agent 读取详细冲突统计，而基线只读取总分，应明确这个信息差异，并通过相同信息条件下的启发式或消融实验区分收益来源。对模型推理、反馈内容和子 Agent 分工的贡献，逐项增加对照，不要求最小版本一次覆盖所有实验。

记录随后端调用次数及总耗时变化的最佳有效结果，以及模型调用次数、token 用量和可获得的费用数据。玩具模型很快时，模型调用可能成为主要耗时，减少仿真次数并不自动意味着总时间更短。

使用多个随机种子复测，并保留不参与搜索的访问流用于最终评价。测试结果不能反复用于调整策略后，仍被当作未见负载上的表现。

需要真实的模型决策参与，才能评价 Agent 的贡献。手写启发式或人工提交候选可以用于调通接口，但应单独标记。

实验记录应包含 DSL、假设、工作负载标识、硬件配置、后端版本、随机种子和结果。复用结果时，这些影响评价的输入需要匹配。

模型服务、模型版本或标识、提示词版本及可用的生成参数也应记录。评价器能重放已保存的候选，不代表模型每次会重新生成相同的候选序列。

## 下一轮：Agent 主导的受控探索

下一轮优先直接评价 Agent 的探索闭环。已有规则实验提供开发样例和失效机制；继续改进联合变化统计，可作为支线或可选分析工具。

1. **固定任务与信息边界。** 约定合法 DSL 子空间、目标函数、共同起点、工具集合与性能评价预算。已看过的反例作为开发数据；冻结提示词和流程后，再评价新的任务。小空间精确最优仅供事后分析，不向搜索过程泄露。
2. **让 Agent 逐轮决定行动。** 根据负载特征与历史反馈提出假设，自主构造候选，选择诊断统计或限定预算的局部搜索，并决定何时改变方向。每轮记录可检验的预测、动作、工具结果及后续调整；这些记录用于追溯，能力结论依赖对照实验。
3. **保留有竞争力的对照。** 比较冻结的启发式、随机/局部等搜索、模型一次性提案和反馈驱动 Agent；工具增强版本另与相同工具的固定调用流程比较。Agent 委派的搜索所消耗的每次后端执行，都计入同一总预算。
4. **检验 Agent 决策的增量。** 观察其能否在反馈不符合预测时调整假设、跨多个原语提出有效修改，以及将预算用于有价值的实验。用去掉反馈、去掉诊断信息或替换自主工具选择等消融检验作用，并报告多次独立 Agent 运行的波动与失败。
5. **报告质量、成本与真实任务适用性。** 比较最佳策略随评价次数的变化、达到预先约定质量所需的评价次数，以及包含模型和分析工具的总成本。同步取得有实际来源的请求数据，之后用更真实的后端复核候选排序和收益。

主线的核心问题是：**面对新负载与有限的昂贵评价预算，Agent 能否通过自主诊断、候选构造和实验规划，提高内存策略探索的质量或效率？** 当前仍可通过对话文件接口试验；若要建立可重复、可计量的 Agent 比较，需要进一步记录并固定模型、提示与执行过程。

## 开发阶段与验收标准

| 阶段 | 主要产物 | 验收标准 |
| --- | --- | --- |
| 1. 最小评价流程 | 访问流生成、DSL 解释与合法性检查、玩具性能模型、实验记录 | 给定候选可完成全部请求并输出指标；非法候选明确失败；固定输入可重放 |
| 2. 策略探索 | 手工与随机基线、真实模型驱动的母 Agent、预算控制 | 母 Agent 能读取反馈继续提案；输出同预算比较记录，准确记录失败与成本 |
| 3. RTL 路线 | 地址映射模块生成、独立参考检查、RTL 仿真 | 可对比映射输出并报告覆盖范围；失败时保存可重现的反例 |
| 4. 子 Agent 分析 | 性能与 RTL 两个子 Agent、结构化反馈汇总 | 原始事实与解读可追溯；不同候选结果不混用；能完成母子 Agent 反馈循环 |
| 5. Ramulator 接入 | 适配层与固定版本的时序仿真配置 | 在相同实验边界下复测候选，报告与玩具模型结果的差异 |
| 6. 扩展研究 | 更强的搜索基线与混合搜索，更真实的 KV 访问、布局、多介质放置或调度原语 | 分别评价搜索方法与新增自由度，为后者补充语义、成本、验证方法与相应基线 |

工程成功与研究成功分别判断：前者要求流程可运行、结果可追溯、实验可重放；后者需要对照实验支持 Agent 带来收益。Agent 未胜过基线也是有效研究结果，不影响最小工程闭环的验收。

当前阶段 1 已完成，阶段 2 已跑通文件接口并记录首轮结果；阶段 3 已生成 RTL，尚未执行仿真。阶段 4–6 尚未实现。运行步骤见 [运行指南](TOY_GUIDE.md)，验证范围与环境记录见 [实验解读](INITIAL_RESULTS.md)。

第一版静态映射、固定布局/单介质/调度、JSON 原语和母子 Agent 分工属于当前设计约定；平台选择仍未确定。允许修改控制器映射是玩具假设，长期可选择定制硬件、既有 GPU 软件或多介质方向。是否扩展工程，应由前面的真实收益证据决定；具体环境资源见运行指南。
