# 研究定位与下一阶段

更新日期：2026-10-28。依据为 20 篇论文的有范围精读和已有玩具实验，不代表论文独立复现或已经建立的 Agent 优势。[文献指南](literature.md)负责阅读路线，[精读笔记](reading-notes.md)保留页码证据、问题台账和认识修订。

## 当前判断

主攻方向是：**由 Agent 在有限评价预算下，根据负载特征与数据生命周期，主导可实现内存策略的探索。** 纯地址位搜索保留为基础对照。已实现 [KV 布局与介质映射组合执行](kv-layout.md)，固定负载与硬件、由候选改变策略；此前静态布局诊断验证了读写传输取舍。联合路径尚无新的 Agent 对照，真实平台上的生命周期取舍与系统净收益仍待检验。

**当前优先级：继续完善 DSL、执行语义及验证，暂不投入新一轮 Agent 优化竞赛。** 现有模型过于简化，启发式解决其中某任务只说明该模型内的结果，不能据此限制后续系统能力开发或判断 Agent 的总体价值。工程诊断继续用于查错和核对机制。

后续研究仍需回答强机制之外的余量及 Agent 的决策增量；同权限、信息、工具与预算比较。扩大空间或接入 Ramulator 本身不保证 Agent 优势，已有成绩及失败记录保留其原始范围。

<a id="agent-mainline"></a>
## 主线与支线

Agent 的主力地位体现在候选构造、瓶颈假设、实验选择、工具调用与预算分配。仿真、验证及局部数值搜索由确定性工具执行，最终按结果评价 Agent 的决策；不要求它自己实现所有工具。

- **主线**：检验持续探索的质量与成本，比较通用 Agent 循环、强搜索器和机制消融。
- **支线**：发现可复用规则、内存机制或任务表征；分别验证新颖性、适用条件和完整成本。
- **支撑**：可信负载、合法控制范围与可追溯测量。工程流程成功和研究贡献成立分别验收。

<a id="agent-rule-discovery"></a>
**“Agent 帮助发现了一个可以固化的规则。规则一旦写出来，执行它当然可以比重新推理更便宜。这本身可能是 Agent 的一种有价值的定位。”** 保留这一认识，但它是支线。规则可成为后续 Agent 工具、强基线或部署实现；需分别记录一次性发现成本和每次复用成本，并保存反例。首轮 column 规则来自事后观察，不能证明发现效率优于人工或其他搜索方法。[实验过程](experiments.md#agent-rule-discovery)

## 两条平台路线

平台暂不限定，先比较实际自由度。下表是基于文献与当前项目状态的研究建议。

| 维度 | 路线 A：可修改控制器/定制硬件 | 路线 B：现有 GPU 推理软件 |
| --- | --- | --- |
| 优化对象 | 布局、分配与可实现的控制器映射协同；选 NPU/PIM 子路线时还需考虑计算访问组织 | KV 布局、分块、分配、页管理及访问组织 |
| 可控制范围 | 以架构/IP 为边界，确认地址转换、区域粒度、命令和必要硬件改动；位选择/XOR 只是其中一层 | 以设备、驱动和框架已开放接口为边界 |
| 关键相关工作 | [SDAM](literature.md#r02)、[Flatfish](literature.md#r03)、[XOR 数学模型](literature.md#r04)；NPU/PIM 子路线重点对照已读的 [PFM](literature.md#r14)、[PATTON](literature.md#r15)、[UMDAM](literature.md#r20) | [PagedAttention](literature.md#r12) 与 [vAttention](literature.md#r13) |
| 评价方式 | DRAM 时序仿真及可信请求模型；必要时加入系统仿真、RTL 综合/验证或原型 | GPU 实测、系统剖析与端到端推理评价 |
| 主要难点 | 请求流真实性、映射与调度耦合、实现成本、切换时的数据一致性 | 区分缓存、合并访问、kernel 与分配收益；既有系统基线很强 |
| 有价值的产物 | Agent 探索证据，以及可实现的联合策略、适用条件与完整成本 | Agent 探索证据，以及可部署的数据组织与分配方法和完整开销下的收益 |
| 与当前原型的距离 | 已有对象/生命周期前端与受限管理策略；仍缺真实计算依赖、校准成本和具体控制器约束 | 已有布局/分配表达，但需对接真实框架与 kernel、限定可控接口；当前位映射 DSL 不能直接部署 |
| 适合的团队资源 | 控制器、RTL、体系结构或仿真经验 | GPU、推理框架与 kernel 开发经验 |

现有 GPU 的虚拟内存/分配控制能力不能直接视为可重编程的 HBM bank 映射。定制 NPU/PIM 的设计也不能直接作为普通 GPU 的能力证明。具体 IP 的限制见 [厂商资料](literature.md#vendor-docs)。

分析 KV 问题时，沿着下面的因果链检查，而不是从张量形式不同直接跳到映射需求不同：

```text
KV 结构与数据布局
    → kernel 访问顺序与分配
    → 缓存、请求合并、地址转换
    → 到达控制器的请求流
    → 地址映射与调度
    → 介质执行和最终性能
```

这条链还包含反馈：容量不足可能触发 eviction/recompute，完成事件可能推迟后续计算与请求生成。布局或分配改变这些事件时，应固定上层逻辑工作负载，允许下层请求随策略变化；固定物理请求轨迹只适用于明确保持流量不变的子问题。

<a id="minimal-system-task"></a>
## 优先收敛的系统问题

**优先候选是 KV 块生命周期中的“追加写入—后续读取/归约—容量占用”取舍。** 这是从 PFM/PATTON 等工作提炼的问题方向，不是已经选定的平台或新机制。现有专门方案已解决部分问题，下一步必须说明剩余问题在哪里，不能把重现其策略当作创新。

开发时显式声明抽象平台的可控操作，后续按具体平台约束收敛。NPU/PIM 的读写冲突需要相应命令与架构支持；普通 GPU 需核实 kernel、分配和容量权限，不能直接采用 PIM 代价模型。HBM 仍是主要背景，AiM/GDDR6 证据保留介质与架构边界。

| 逐步考虑的子问题 | 必须同时计入的取舍 | 应先比较的机制基线 |
| --- | --- | --- |
| 固定容量下的一种 KV 块：写入友好布局与读取/归约友好布局 | 完整读写路径、操作次数、有效传输及结果回收 | 静态布局、解析代价选择、结构化搜索 |
| 若生命周期确有额外影响，再加入 partial/full、填满提交与早停 | 未满块读取、搬移、暂存和目标预留、发布/回收顺序 | 固定提交策略、阈值策略、适用平台的已有专门机制 |
| 若容量压力是主要矛盾，再加入共享、淘汰与重计算 | 有效容量、共享命中、额外计算及服务完成时间 | 容量感知分配与缓存策略，并做机制消融 |

上表是系统问题方向，不是要求每扩展一层先证明 Agent 胜过启发式。多对象、混合模组/池和有限管理策略已经接通；本轮已补 GC 策略搜索、详细 SSD 与合成跨层任务，后续仍需代表性真实输入与可信评价，不一次实现完整控制器和推理服务。

任务规格应写清平台权限、对象/操作/状态、合法策略、请求依赖、容量与转换成本、正确性、目标、强基线及开发/未见划分；先用手算核验代价关系。

**当前进展：** 对象身份、创建/失效、读写、硬件与权限固定；`kv_layout` 决定相对布局和初始目标，管理策略决定预留/迁移，介质策略决定内部位置。逐资源计容、字节事务重放及共享链路评价已接通，复制、发布、释放与双份容量均计费；迁移仍限写满的单对象单区域组。NAND 可选通道/die 条带、前台 GC 阈值/选块；详细 SSD 复用同一 NAND 层并限制控制器权限。未满对象迁移后置。历史单对象传输模型的三个任务均被解析选择达到枚举最优，见[诊断](experiments.md#kv-layout-v1)；新增能力只做工程验收，尚无新的 Agent 对照，也未对应选定的 GPU/PIM 实现。

| 场景 | 固定输入与可控边界 | 设计职责 |
| --- | --- | --- |
| 多个混合模组，例如 8 个 HBM＋NAND 模组 | 模组内介质、容量、连接与控制器权限；分别定义 DRAM/NAND 操作 | `kv_layout` 选择静态目标及组织，各介质独立解析位置与执行操作 |
| 内存与封装 SSD 组成的池 | 池引用实际资源；主机看到逻辑块，内部设计须另声明控制器权限 | 现有块设备抽象评价主机接口；详细模式已复用同一 NAND DSL/执行层，仅对开放控制器搜索 |
| 运行时资源管理 | 负载规定数据需求和逻辑生命周期，平台限定可用动作 | 先固定管理实现，再开放分配、回收与迁移；不得免费重新绑定已有数据 |

例如 K/V 各占两个 4 KiB 存储 chunk：拼接为 `K0,K1,V0,V1`，交织为 `K0,V0,K1,V1`。chunk 是布局组合单位，不自动等同于 KV 逻辑块、分配页或 NAND 页。静态目标选择可继续放在 `kv_layout`；分配/回收/迁移需要运行时状态，但职责拆分不要求新造一种语言。

新路径保留对象与目标身份，逐资源核对容量并独立重放实际事务。NAND 数据失效不等于空间已擦除可用；主机侧 SSD 逻辑地址也不等于内部 NAND 页。具体字段边界、执行顺序和逐批验收只在[开发计划](development.md#implementation-plan)维护。

<a id="evaluation-method"></a>
## 如何检验 Agent 的贡献

先冻结平台权限、任务、合法策略、主要目标、成本边界和开发/未见划分。固定流量可用内存完成时间；涉及容量、重计算或批处理时要计入服务代价，不能以行命中率或单个 kernel 加速代替系统净收益。

| 要区分的作用 | 必要对照或记录 |
| --- | --- |
| 优化余量与搜索质量 | 合理默认、专门机制、结构化搜索，以及适配任务的随机/局部/进化或贝叶斯优化 |
| 模型初始先验与逐轮反馈 | 一次生成、匹配调用次数的逐轮无新反馈、逐轮真实反馈；保存反馈前预测和之后行动 |
| 工具与 Agent 决策 | 同工具由固定流程调用或由 Agent 自主选择；必要时移除 Agent 建议 |
| 主动诊断与分工 | 诊断/重启/恢复区域评价计入预算；独立子 Agent 的调用与协调成本单列 |
| 经验复用与泛化 | 冷启动和历史复用分开；冻结方法后在未参与开发的负载上评价，保存负迁移和最差退化 |

每个候选在每个任务上的真实后端执行分别计数，包含初始化、校准、补测与失败；缓存命中、非法提案、低保真查询、RTL 与模型调用分账，并限制提案数或总时间。20 次只是起始预算，同评价数不等于同总成本。

记录空间、信息、工具版本、种子、候选/假设和输入摘要；能获得时记录模型、提示、生成参数、token、费用、资源和时间。提示调参与数据准备成本单列。只报最好一次、把多种子最佳值计作一次预算，或给 Agent 更多权限，均不构成公平对照。

独立重复模型探索并使用多随机种子强基线。固定候选重放只证明程序一致性，不能替代模型重复；已读过的任务是开发数据。模型是否正确诊断、能否生成合法且多样的候选、能否选中好候选，应分别观察。

值得检验的四个问题：反馈能否纠正有代价的假设；主动诊断能否节省评价；联合策略是否优于静态/顺序选择；经验何时失效。优先离线探索或部署前选择，运行时可以执行固化规则；动态改写已有数据的位置另需一致性与迁移成本。

正式比较 Agent 前，应在代表性任务和可信评价下检查相对强方案的剩余空间；它不是继续完善 DSL 的前置门槛。多个未见任务中的同条件持续改善，才支持主线优势。

<a id="next-agent-study"></a>
## 已有实验与下一轮 Agent 证据

V2、失败复盘与 V3 已完成，结果集中见[实验总览](experiments.md)。它们提示应保留有潜力的非最优中间候选、区分当前请求与前序积压，但详细反馈既有改善也有退步，尚未建立稳定优势。旧任务只选择一套静态映射，未验证运行时迁移；已见反例和 oracle 均作为开发资料。

**后置的协议草案，近期不执行：** 待 DSL、代表性任务和评价能力足够后，再隔离反馈贡献。暂拟共享 5 个随机合法、去重后的初始候选及其评价，总计 20 次上限、剩余最多 15 次；不同时测模型 warmstart。预算随未来任务重新冻结。

| 组别 | 后续探索 | 要回答的问题 |
| --- | --- | --- |
| A：强传统搜索 | 根据真实反馈搜索，具备多步扰动/重启等适用机制 | Agent 相对强搜索的总体收益 |
| B：模型一次生成 | 只看公共初始数据，一次冻结后续候选 | 初始语义先验与样本能做到什么 |
| C：模型逐轮、无新反馈 | 多次提案，保留初始数据及已提候选，但不读取后续真实结果 | 多次调用自身的作用 |
| D：Agent 逐轮反馈 | 与 C 匹配模型设置及资源上限，依据真实反馈改变策略 | 重点比较 D−C，识别反馈增量 |

四组与旧 V3 的“提示 × 反馈粒度”实验不同。C/D 使用独立上下文；无反馈组隔离日志和工具耗时等泄露路径。合法性、去重、权限和通用工具一致；提案不足、超时、非法与重复均记录，不允许无限重试。共同起点用随机初始化而非为 Agent 人工挑选，具体抽样方式随新空间冻结。

保存事前假设、方向预测、实测与后续行动；分别诊断候选池质量和选择能力，事后评价单列费用、隔离结果。主动工具调度还需对照固定流程；新的诊断/记忆/规划机制需做移除消融，四组本身不证明新颖性。理由见[协议草案](reading-notes.md#feedback-protocol-draft)；数字可在实验前调整，不得根据测试结果追改。

当前可继续使用对话文件接口；建立可重复、可计量的比较时，需记录并固定模型、提示与执行过程。

## 先完善设计与执行能力，再评价 Agent

| 顺序 | 主要产物 | 进入后续工作的条件 |
| --- | --- | --- |
| P0–P4，已完成 | 多对象布局、模组/池、DRAM / 裸 NAND / SSD 执行、独立重放 | 逐资源计容、内容与操作/链路手算通过；SSD 不越权控制内部 FTL |
| P5，有限策略已完成 | 预留、整对象迁移、NAND 页条带/前台 GC 策略、详细 SSD | 生命周期固定，容量余量、复制/擦除与并行竞争计费；独立核对内容与操作 |
| P6，条件式推进 | 可信后端、代表性负载、必要 RTL 与正式 Agent 对照 | 评价覆盖目标收益与代价；正式比较同权限、信息、工具与预算 |

工程成功与研究成功分别判断：前者要求流程可运行、结果可追溯、实验可重放；后者需要对照实验支持 Agent 带来收益。Agent 未胜过基线也是有效研究结果，不影响最小工程闭环的验收。

已有实验用于回归和开发诊断；具体实施以[开发计划](development.md#implementation-plan)的依赖、完成标准及反例为准。具体平台决定合法权限及成本；不在现有简化模型上反复比较 Agent 胜率，也不要求一次完成全部系统。

后端和验证按任务选择：软件布局/分配先检查内容、状态及数值；改变控制器才需要相应 RTL，综合得到的缓冲、延迟等成本应反馈性能模型。时钟级命令合法不等于目标控制器已校准，也不证明 KV 内容正确。分析子 Agent 是可选研究机制，不是所有策略的必经环节。

运行契约见[运行指南](development.md)，旧实验见[实验总览](experiments.md)，主要近似见[能力边界](development.md#model-limits)。混合资源、有限分配/迁移和 NAND 页分布已可作为候选评价，尚未进行这些联合空间上的新 Agent 对照。策略在离线选定后按规则运行，没有常驻 Agent 在线管理内存。继续暂停 Ramulator / MQSim 实际运行及环境安装。两者的接口准备不等于完成校准；原生 MQSim 内部规则也不等于当前 NAND DSL。第 5 步另行讨论。

## 文献如何改变研究与开发原则

下表是跨论文形成的判断。具体实验条件与作者报告的范围以链接中的精读记录为准，不能把不同平台、基线和指标下的加速比合并比较。

| 文献证据 | 当前认识 | 对后续工作的约束 |

## 新 DSL 与系统模型的开发约束

DSL 是领域语义的表达方式，不自动意味着搜索空间。负载和硬件作为固定输入；候选 DSL 只描述本轮允许改变的实现策略。JSON 可以直接承载这些语义，不必再转成另一种文本语言。先固定任务与允许控制范围，再让 Agent 组合原语；不能通过少读数据、取消写入、降低精度或扩大硬件资源获得假收益。新原语要定义实现权限、正确性与成本，经过独立检查进入新协议后才能比较。

统一候选可以组合多层策略，教学中的每个地址层级不必成为独立搜索空间。当前省略 VA/页表与缓存；需要它们提供的决策或成本时再展开。地址来源诊断用于核对映射过程，不构成精度或性能收益证据；基础解释见[张量到 DRAM](tensor-to-dram.md)。

| 层次 | 需要明确的语义与检查 |
| --- | --- |
| 任务与策略 | shape、dtype、逻辑操作、容量与目标固定；候选只改变允许的布局、分配或转换。原语表达机制组合，不以 `use_PATTON` 代替设计空间 |
| 状态与正确性 | 应用阶段来自负载，partial/full 由进度和块容量推导，转换时机由策略决定；按需要引入暂存、提交、共享/回收；检查跨对象范围、写后读、发布顺序及数值语义，局部可逆不等于全局正确 |
| 请求生成 | 静态映射可固定流量；依赖任务由前驱完成产生后续 ready；分配、eviction/recompute 改变流量时固定逻辑任务，不能共用一份最终物理轨迹 |
| 容量与转换 | 计入未满块读写、临时副本、目标预留、搬移及元数据，不只计算写入加速 |
| 时间与模型 | 分清 ready、accepted、completed 及读写完成；反压不是计算依赖，写接受不是可见，后端驻留不是纯器件延迟。用手算与参考执行检查，再按目标校准 |
| 记录与归因 | 评价绑定任务、策略、前后端版本；提案、执行、诊断和模型成本分账。工具事实与模型解释分开，非法、失败、未执行分别记录，`not_run` 不是通过 |

表达式相同、映射函数相同、模型中性能等价、一次实验同分是四件事。旧 720 排列在字段重编号下有 180 个已审计等价组，也有局部障碍；名义空间大小不等于搜索难度，更不意味着普通凸优化。见[有效空间审计](reading-notes.md#round-7)。增加语义时同步开放给强基线，更新合法性和 oracle，不能把表达能力收益记作 Agent 优势。

软件布局优先验证内容与状态；改变硬件时按需加入 RTL/综合，并把新增流水级、缓冲和转换成本反馈性能模型。工具修复后记录新版本，重新评价；不能混用不同实现的成绩。依据见[生命周期](reading-notes.md#kv-research-scope)与[后端契约](reading-notes.md#backend-contract)。
