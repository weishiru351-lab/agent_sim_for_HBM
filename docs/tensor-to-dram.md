# 一个张量元素怎样到达 DRAM：从布局、页表讲到介质地址

本文从一个元素讲起，不要求读者了解操作系统或内存控制器。先读第 1–5 节理解地址链，再读第 6–8 节了解分散放置、SSD 和本仓库的实现。配置细节另见[运行与开发](development.md)。

贯穿全文的例子：**32×32 的二维张量 T，每个元素 2 B，按 16×16 分块的 NZ 方式存储；OS 页为 4 KiB，DRAM 传输粒度为 64 B。** 下标从 0 开始；B 表示字节，1 KiB = 1024 B；`0x` 开头的数是十六进制，`0x400 = 1024`。

```text
张量元素 T[0,16]，共 2 B
    ↓ NZ 布局决定它在缓冲区中的位置
对象内偏移 1024 B
    ↓ 加上缓冲区起始虚拟地址 0x10000000
虚拟地址 0x10000400
    ↓ 页表：虚拟页 0x10000000 → 物理页 0x80000000
物理地址 0x80000400
    ↓ 按 64 B 划分
块起始地址 0x80000400，块内偏移 0
    ↓ 控制器确定目标，并按地址映射规则解码
channel / bank / row / column，以及块内的两个字节
```

这里的地址均指元素的**第一个字节**，第二个字节的地址加 1。这条链解释“数据在哪里”；真实读写还涉及缓存、排队和命令执行，不保证一次程序访问就产生一次 DRAM 访问。64 B、4 KiB 和两个基址都是本例假设，不是所有平台的规定。

## 1. 布局：先决定元素在对象内部排第几

张量的 `[行,列]` 是逻辑下标，内存地址则按字节编号。布局负责把前者换成**距离对象起点多少字节**。

先看普通二维、紧凑的按行存储：第一行存完再存第二行。本文用它代表这个例子的 ND 布局，元素 `[r,c]` 的偏移为 `(r×32+c)×2`。因此 `[0,16]` 前面有 16 个元素，偏移是 32 B。

本例的 NZ 把矩阵分成四个 16×16 小块，每块 `16×16×2 = 512 B`：

```text
逻辑矩阵中的位置：       连续缓冲区中的顺序：
       A  B             A → C → B → D
       C  D             每个小块内部逐行存储

各块起点：              A:0   C:512   B:1024   D:1536 B
```

`[0,16]` 正好是 B 的第一个元素。B 前面有 A、C 两块，所以它的偏移是 `2×512 = 1024 B`。布局只是改变存放次序，元素的逻辑名字仍是 `[0,16]`。

| 元素 | 按行存储的偏移 | 本例 NZ 偏移 |
| --- | ---: | ---: |
| `[0,0]` | 0 B | 0 B |
| `[0,16]` | 32 B | 1024 B |
| `[16,0]` | 1024 B | 512 B |
| `[0,17]` | 34 B | 1026 B |

需要自行计算其他元素时，可用下式。`//` 是整除，`%` 是余数；前两项找到大块，后两项找到块内位置。

```text
块行 r1 = r // 16，块内行 r0 = r % 16
块列 c1 = c // 16，块内列 c0 = c % 16
NZ 字节偏移 = (((c1 × 2 + r1) × 16 + r0) × 16 + c0) × 2
```

这是一个确定的二维 FP16 示例；实际 Ascend 格式、分块尺寸和支持算子与数据类型、设备有关。本仓库能表达这个排列，没有实现 Ascend 算子适配或真实格式转换。[Ascend C 开发指南：矩阵分形与格式转换](https://www.hiascend.com/doc_center/source/zh/CANNCommunityEdition/700alpha003/operatordevelopment/ascendcopdevg/CANN%207.0.0.alpha003%20Ascend%20C%E8%87%AA%E5%AE%9A%E4%B9%89%E7%AE%97%E5%AD%90%E5%BC%80%E5%8F%91%E6%8C%87%E5%8D%97%2001.pdf)

**连续缓冲区不一定每个位置都有有效元素。** 32×32 恰好分成四块，2048 B 都有用；如果张量只有 17×17：

| 存放方式 | 有效数据 | 布局占用的跨度 |
| --- | ---: | ---: |
| 紧凑按行存储 | 578 B | 578 B |
| 按上述 16×16 规则补齐后分块存储 | 578 B | 2048 B |

多出来的是 padding（填充位置）。分配器还可能额外保留对齐空间，因此“有效数据量”“布局跨度”“分配容量”要分清。数据类型决定每个元素的编码和字节数，布局决定这些字节怎样排列；改成 INT8 等量化方案是另一项决策。

## 2. 虚拟地址：为这段缓冲区取得程序可使用的编号

布局只告诉我们偏移 1024 B，还没有告诉我们整个对象放在哪儿。假设分配器给 T 一个从 `0x10000000` 开始、长度 2048 B 的连续虚拟缓冲区：

```text
缓冲区：[0x10000000, 0x10000800)   左端包含，右端不包含
T[0,16] 的虚拟地址 = 起点 + 对象内偏移
                    = 0x10000000 + 0x400 = 0x10000400
```

程序保存起始指针、形状和布局规则，就能找到每个元素。无需为每个元素、每个 64 B 分别申请一个虚拟缓冲区。

虚拟地址可以理解为程序使用的“门牌号”。它不是 DRAM 容量的直接编号：一个进程的地址空间可以很大，其中只有部分范围可用、已映射；两个进程相同的虚拟地址也可以对应不同物理位置。[Microsoft：虚拟地址空间](https://learn.microsoft.com/en-us/windows-hardware/drivers/gettingstarted/virtual-address-spaces)

因此，“已经用到 X，下一次一定从 X+1 开始”只是一种简单分配策略。实际可以有空洞、对齐、复用和多个分配区域。**一次申请得到连续范围，不代表所有申请彼此相邻，也不代表底下物理连续。** 预留虚拟范围也不等于立即占用相同容量的 DRAM。

## 3. 页表：把程序地址对应到实际物理范围

### 3.1 先拆成页号和页内偏移

以 4 KiB 页为例，相邻 4096 个字节构成一个对齐页面。地址转换时保持页内偏移，只更换页面对应的物理起点：

```text
虚拟页号 = 虚拟地址 // 4096
页内偏移 = 虚拟地址 % 4096
物理地址 = 页表记录的物理页起点 + 页内偏移
```

本例 `0x10000400` 属于从 `0x10000000` 开始的虚拟页，偏移是 `0x400`。假设页表记录该页对应物理页 `0x80000000`，结果就是 `0x80000400`。

页表的工作不是“判断张量应该放到哪个 bank”。职责应分开理解：**分配策略选择物理页；页表保存映射和权限；MMU 硬件在访问时完成翻译；TLB 缓存近期的翻译结果。** 实际页表通常是多级索引，末级记录数据页的位置，不为每个张量元素单独建立表项。TLB 没命中可以继续查页表，并不等于缺页；缺页或权限异常才需要相应处理。[Linux：页表与地址翻译](https://docs.kernel.org/mm/page_tables.html)

### 3.2 虚拟连续，物理可以分散

另取一个 **8 KiB 缓冲区**演示跨页，避免与前面的 2 KiB 张量混淆：

| 对象偏移范围 | 虚拟页起点 | 物理页起点 |
| --- | --- | --- |
| 0–4095 B | `0x10000000` | `0x80000000` |
| 4096–8191 B | `0x10001000` | `0x90003000` |

偏移 1024 B 仍得到 `0x80000400`。偏移 5000 B 则进入第二页：`5000 = 4096 + 904`，所以虚拟地址是 `0x10001388`，物理地址是 `0x90003388`。**不能为整个跨页对象假定一个物理起点，再始终直接加偏移。**

也可以使用两个不相邻的虚拟范围，但此时需要两个基址或分段索引。对一个普通连续指针直接做 `base + offset`，不会自动跳过虚拟地址中的空洞。

### 3.3 谁决定页大小？小对象是否独占整页？

可用页大小由处理器/MMU 支持能力及操作系统决定，应用只能在平台提供的选项中请求。它不由张量大小或 DRAM 突发决定。同一条普通分页映射中，两边的范围大小相同：4 KiB 对应 4 KiB；一条 2 MiB 大页映射需要连续的 2 MiB 物理范围，不能指向任意分散的 512 个 4 KiB 页。[Linux：大页机制](https://docs.kernel.org/admin-guide/mm/hugetlbpage.html)

用户态分配器可以在已经取得的页内分配小对象。对于一个 6 KiB 对象：

| 条件 | 涉及的 4 KiB 页 |
| --- | --- |
| 从页边界开始 | 2 页，使用 4 KiB + 2 KiB |
| 从页内偏移 3 KiB 开始 | 3 页，使用 1 KiB + 4 KiB + 1 KiB |

涉及两页不等于独占两页。内存池可以将尾页剩下的 2 KiB 分给其他对象；若是独立为它保留的两页，剩余空间不会自动交给别的申请。一般公式是 `ceil(((起点 % 页大小) + 长度) / 页大小)`。OS 的预留粒度还可能与页大小不同，例如 Windows 的 VirtualAlloc 就区分两者。[VirtualAlloc 分配规则](https://learn.microsoft.com/en-us/windows/win32/api/memoryapi/nf-memoryapi-virtualalloc)

页表也不负责免费搬数据。若已写入的数据要换到另一物理页，必须安排复制、映射更新和必要的同步，之后才能让读者访问新位置。

## 4. 64 B 传输：一个块里仍有 64 个字节地址

本例假设一次 DRAM 突发传输 64 B。这是一次传输的数据总量，可经多个传输拍完成，不等于一个瞬间传完，也不等于这 64 B 共用一个字节地址。

```text
物理字节地址          所属 64 B 块起点      块内偏移
0x80000400            0x80000400            0
0x80000401            0x80000400            1
0x80000402            0x80000400            2
...
0x8000043F            0x80000400           63
0x80000440            0x80000440            0  ← 下一块
```

计算方法：`块起点 = (物理地址 // 64) × 64`，`块内偏移 = 物理地址 % 64`。T[0,16] 占块内字节 0、1，T[0,17] 占 2、3。同一对齐块能容纳 32 个 FP16 元素，仍然各有字节地址。

一次只需要 2 B，也可能占用一次完整 64 B 传输。访问从块内偏移 60 开始的连续 8 B 会跨两块；从偏移 0 开始则只覆盖一块。实际硬件可能有掩码、缓存或读改写规则，不能把接口粒度、缓存行和应用申请大小混为一谈。64 B 也不是所有 HBM 的规定，例如 AMD 的一个 HBM 控制器接口采用 32 B 突发。[AMD：HBM 事务与对齐](https://docs.amd.com/r/en-US/pg276-axi-hbm/AXI-Considerations)

布局会影响访问覆盖多少传输块。例如只读左上角 A 的 512 B：假设对象起点对齐、所有选中字节允许一起合并、无缓存或预取，ND 每行取 32 B、跨 16 个 64 B 块，传输 1024 B；NZ 的 A 连续，占 8 块，传输 512 B。若改为 32 B 粒度，两者都覆盖 16 块，均为 512 B。

**这个覆盖数不是任何执行方式下都能取得的事务数。** 若一行一行分组且组间没有缓存，NZ 中两个半块访问可能分别付费。本仓库正是按固定访问组分别合并；不能把合并范围的改变误算成布局本身的收益。

## 5. DRAM 映射：把地址编号分派到通道、bank、行、列

可粗略把 channel 理解为传输通路，bank 为能维护各自行状态的存储分区，row 为该分区中的行，column 为行内位置。实际 DRAM 还有 rank、bank group、伪通道等组织；这里采用本仓库的简化几何。

假设有 4 channel，每 channel 有 8 bank，每 bank 有 512 row，每 row 有 1024 个 **64 B 槽位**。最后这项是本仓库 `columns` 的定义，不是直接照搬真实芯片的列引脚数。

```text
总容量 = 4 × 8 × 512 × 1024 × 64 B = 1 GiB
块地址需要 2 + 3 + 9 + 10 = 24 bit
再加 6 bit 块内字节偏移，共 30 bit 目标内字节地址
```

为了把前面的系统物理地址接上，**再假设**这 1 GiB DRAM 占系统物理窗口 `[0x80000000, 0xC0000000)`，控制器先减去窗口起点。因此系统物理地址 `0x80000400` 在这个目标内部是 `0x400`。真实平台的窗口选择和交织规则需要另查，不能普遍套用“减基址”。

在本仓库的默认映射中，目标内字节地址从低位到高位分工如下：

| 位段（最低位为 bit 0） | 内容 | 位数 |
| --- | --- | ---: |
| 0–5 | 64 B 块内字节偏移 | 6 |
| 6–7 | channel | 2 |
| 8–10 | bank | 3 |
| 11–20 | column 槽位 | 10 |
| 21–29 | row | 9 |

所以 `0x400 = 1024` 除以 64 得到块编号 16，默认解码为 **channel 0、bank 4、row 0、column 0**；元素的两个字节位于块内偏移 0、1。

地址位 DSL 修改的是这个**块编号**，不会交换元素的数值或块内的字节。对块编号的 bit 0 与 bit 4，三个候选产生：

| 映射规则 | 变换后块编号 | channel / bank / row / column |
| --- | ---: | --- |
| 不变 | 16 | 0 / 4 / 0 / 0 |
| 交换 bit 0 与 bit 4 | 1 | 1 / 0 / 0 / 0 |
| `bit 0 ← bit 0 XOR bit 4` | 17 | 1 / 4 / 0 / 0 |

交换重新安排位的职责；XOR 让一个输出位同时受多个输入位影响。不同访问规律可能因此分散到不同通道/bank，或者破坏原有行局部性。它们不是必然加速，完整例子见[地址位 DSL 教程](dsl-tutorial.md)。同一控制器的读写必须遵守一致映射，不能对每个对象任意换一套解释；已有数据上切换映射也不能忽略搬运或重新初始化。

## 6. 想把张量分散存放，应改哪里？是否需要每层都有 DSL？

首先说清楚“分散”的目标：只是让两个指针数值相距很远，还是让数据进入不同物理页、不同设备、不同 channel？这些效果不等价。

| 想改变的事情 | 应考虑的控制点 |
| --- | --- |
| 哪些元素在同一连续片段中 | 布局、切片或分段规则 |
| 对象的不同部分进入不同内存池/设备 | 区域选择、分配与条带放置 |
| 虚拟连续，但物理页分散 | 平台允许的物理页分配与绑定 |
| 同一物理地址流使用不同 channel/bank | 开放控制器的地址映射规则 |

若把张量拆成两个虚拟缓冲区，访问公式会变成“元素下标 → 片段号和片段内偏移 → 该片段基址 + 偏移”。使用者必须理解这个接口，或者付出收集、复制的开销；不能仍假定原来的单指针连续 NZ 算子能直接使用它。

本例每个 A/B/C/D 小块只有 512 B。一条普通 4 KiB 页映射不能独立移动其中某个 512 B 小块；需要另行分配、复制，或通过其他层次的条带/控制器映射取得目标效果。**虚拟地址远，不保证物理地址远；物理地址远，也不保证 channel 不同。**

本项目采用一个完整候选组合可控策略，内部沿用布局、管理、介质映射模块。可以把静态地址关系合成为“逻辑字节 → 目标及位置”，无需每个中间层都建立独立 DSL。虚拟页表没有提供新的可控决策或评价影响时，可明确省略。

但统一描述仍须遵守平台权限、对齐、容量及消费者要求，并计算实际过程：相同最终位置，若一种方案多做格式转换、迁移或 NAND 回收，成本就不同。仅比较最后的坐标集合不足以判定两个候选等价。

## 7. 如果目的地是 SSD，后半条链会变成什么？

布局仍先确定字节序列。若把它存成文件，典型目的地址链是：

```text
对象内偏移 → 文件内偏移 → 文件系统分配的设备逻辑块
          → SSD 接收的 LBA → FTL 映射 → NAND 物理页及页内偏移
```

LBA 是设备逻辑块编号；FTL 是闪存转换层。文件系统记录文件到块的对应关系，设备内部再管理块到闪存位置的关系。逻辑地址不变时，更新或回收可能改变实际 NAND 位置。[ext4 文件块映射](https://docs.kernel.org/filesystems/ext4/ifork.html)；[KIOXIA：逻辑到物理地址转换](https://www.kioxia.com/content/dam/kioxia/shared/business/memory/mlc-nand/asset/productbrief/KIOXIA_Understanding_Logical_Block_Address_Tech_Brief.pdf)

源缓冲区的虚拟/物理地址与目的文件偏移/LBA 是传输的两端，不能直接把源 DRAM 地址换算成目的 LBA。直接块设备访问可以绕过文件系统；裸 NAND 则由主机或自定义控制器承担更多管理职责。

OS 内存页、SSD 逻辑块、NAND 编程页与擦除块是不同单位。NAND 通常按页编程、按块擦除，更新需要考虑旧数据保留和空间回收；不能直接套用 DRAM 的任意覆盖写模型。具体粒度和限制需由器件及接口定义。

### 跑本文的小例子，查看 T[0,16]

[`examples/tensor_addressing.json`](../examples/tensor_addressing.json) 已写好 32×32 形状、NZ 初始设计和上述 DRAM 几何，先写入所有行，再读取 `[0,16]`。它从**目标内地址 0**开始；教程里的虚拟基址和系统物理窗口只是解释背景，不在模拟器中伪造。

在仓库根目录用 PowerShell 执行。先将完整候选另存到本地临时目录，再做一次带细节的评价，只显示最后一笔读取：

```powershell
python -c "from agent_design_search.json_io import read, save; save('.local/tensor_design.json', read('examples/tensor_addressing.json')['initial_design'])"
$evaluation = python -m agent_design_search evaluate .local/tensor_design.json --task examples/tensor_addressing.json --include-events | ConvertFrom-Json
$evaluation.metrics.request_sources[-1] | ConvertTo-Json -Depth 8
```

输出 `metrics.request_sources` 的最后一项是这次读取，关键内容如下（省略其他字段）：

```json
{
  "object": "T", "kind": "read", "workload_event": 1, "group": 32,
  "address_space": "dram_target_bytes", "address": 1024,
  "granule_bytes": 64, "valid_bytes": [0, 1],
  "dram_location": {"channel": 0, "bank": 4, "row": 0, "column": 0},
  "byte_origins": [
    {"index": [0, 16], "element_byte": 0, "object_offset": 1024,
     "region_offset": 1024, "target_address": 1024, "block_offset": 0},
    {"index": [0, 16], "element_byte": 1, "object_offset": 1025,
     "region_offset": 1025, "target_address": 1025, "block_offset": 1}
  ]
}
```

`address` 是事务的对齐起点；`byte_origins` 是这笔事务实际使用的字节。三种偏移本例恰好相同，加入对象组合、非零区域起点或跨目标条带后就可能不同。`group` 标识实际提交组，`workload_event` 指向输入事件：一次 append 可以产生多组。`virtual_memory: "not_modeled"` 明确说明没有进行页表翻译。

本例最后的读取有效数据为 2 B，接口传输 64 B。加上前面的逐行写入，整次执行有效读写共 2050 B，传输共 4160 B；这来自固定分组与无缓存假设，不是 NZ 的硬件性能结论。去掉 `--include-events` 就只返回通常的指标，避免逐字节诊断使反馈过大；完整搜索继续使用会话来累计预算。
